# Android release: signing, verification and the local procedure (Issue #72)

> **Status.** The signing configuration, the verifier and the local procedure are
> implemented and tested with **disposable keys only**. They have also been used once with the real
> Cadena upload key, by the key holder on the build workstation, to produce release **1.0.4+1000035**,
> which Google Play accepted and published (section 9). The repository, its tests and its workflows
> never hold or use a real key. Nothing here publishes or uploads anything: a verified release is **not**
> authorization to publish. Context: [RELEASE_POLICY.md](RELEASE_POLICY.md),
> [RELEASE_SIGNING_ARCHITECTURE.md](RELEASE_SIGNING_ARCHITECTURE.md),
> [RELEASE_VERSIONING.md](RELEASE_VERSIONING.md), [BUILD_CONFIGURATION.md](BUILD_CONFIGURATION.md).

## 1. The signing strategy (decided, Issue #72)

| Identity | Held by | Used for | Fingerprint (SHA-256) |
|---|---|---|---|
| **Google Play app-signing key** | Google (Play App Signing). **Unchanged**; Cadena never holds it | The APKs that Google Play delivers to devices | `13:52:D9:EE:63:8B:89:6B:53:2E:C6:F3:79:30:DA:42:5D:84:F3:55:0A:64:66:58:F3:9B:2E:22:22:AC:9F:CB` |
| **Upload key (new)** | CadenaBitcoin, generated by the CFO | Signs the AAB that is uploaded to Google Play; also signs the locally built APK | `84:E9:8F:84:18:04:85:E7:8F:27:BF:B8:A3:DD:04:6E:41:F3:B5:6E:71:EF:0B:0F:9D:28:92:51:59:57:A9:9E`, active; recorded in `config/release/android_signing.json` (`upload.active_sha256`) |
| Upload key (old) | Not available to this project | **Not to be used** | `23:E0:C7:51:D3:7D:A0:58:AC:60:0F:3B:5E:4B:52:36:19:5F:F1:82:8E:8E:8B:06:18:C8:F1:DC:7C:7F:62:94` (`do_not_use`) |
| Debug key | Every build machine, ephemeral on CI | Compile validation only | never a release |

The application IDs are `com.cadenabitcoin.mobile.signer` (production, the package of the
app on Google Play) and `com.cadenabitcoin.mobile.signer.staging`.

**Consequence the maintainers must keep in mind.** A locally built APK is signed with the
**upload** key. Google Play re-signs its own APKs with the **app-signing** key. The two
certificates differ, so **an APK signed locally cannot update an installation that came from
Google Play, and the reverse** (Android refuses an update signed with another certificate;
the user must uninstall first and loses the app's data). The verifier labels the two
differently (`release-local` and `play-signed`) so that they are never confused. If the
website APK must be update-compatible with Google Play installations, distribute the **Play-signed
universal APK** that Google Play Console offers for download (App bundle explorer, Downloads,
if offered for this app) and verify it with `--signing play`; the locally signed APK is then
the build-reproducibility and audit artifact. Which one goes to the website is a release-authority
decision, not made here.

## 2. How the build is signed

`android/app/build.gradle.kts` signs the `release` build type in one of two modes, chosen
explicitly by the environment variable `CADENA_SIGNING`:

| `CADENA_SIGNING` | Result |
|---|---|
| unset or `validation` | Debug key. This is the credential-free compile validation of CI (`build-variants`, `android-ci-validation`). **Not distributable**; the release verifier refuses it |
| `release` | The keystore supplied from outside the repository (below). **The build fails** if anything is missing or wrong; there is no fallback to the debug key |
| anything else | The build fails |

In `release` mode Gradle reads, from environment variables or from a Java properties file
named by `CADENA_SIGNING_PROPERTIES` (an environment variable wins over the file):

| Property | Environment variable |
|---|---|
| `storeFile` | `CADENA_KEYSTORE_FILE` |
| `keyAlias` | `CADENA_KEY_ALIAS` |
| `storePassword` | `CADENA_KEYSTORE_PASSWORD` |
| `keyPassword` | `CADENA_KEY_PASSWORD` |
| (none) | `CADENA_EXPECTED_CERT_SHA256`, **required** |

The keystore and the properties file must be **outside the repository directory**. Before
anything is signed, Gradle opens the keystore and compares the SHA-256 fingerprint of the
certificate with `CADENA_EXPECTED_CERT_SHA256`; a mismatch fails the build. Neither a password
nor a key is ever printed. APK Signature Schemes v2 and v3 are enabled (v3 is what a later key
rotation needs).

**The production signing identity signs the production application only.** In `release` mode, once the
task graph is known and before anything is compiled or signed, Gradle fails the build if it would run any
task of the release variant of a flavor other than `production` (`assembleStagingRelease`,
`bundleStagingRelease`, `packageStagingRelease`, ...). That covers `flutter build apk|appbundle --flavor staging`,
a direct `./gradlew` invocation and the flavor-less aggregates (`assembleRelease`, `bundleRelease`, `assemble`),
which assemble every flavor. The flavors to refuse are read from the `productFlavors` declarations, so a flavor
added later is refused without an edit. Debug variants hold no release identity and are not affected, and
validation mode (no `CADENA_SIGNING`) builds every flavor as before. A staging build is therefore either a
debug-signed validation build or not made at all; there is no Android staging signing identity (section 8).

Prefer passing the two passwords through the environment (typed with `read -rs`, not on a
command line that lands in a shell history). The CI workflows do not set any of this; a
workflow that signs would be a separate, reviewed change with protected environments.

## 3. What the verifier checks

`tool/verify_android_release.py` reads an artifact as a stranger would. It needs `aapt2`,
`apksigner`, `zipalign` (Android build-tools), `bundletool` (`BUNDLETOOL_JAR`, the pinned
1.18.3), `keytool` and `jarsigner` (JDK 17), and Python 3 with the standard library.

| Area | Checks |
|---|---|
| Identity | Application ID, display name, `versionName`, `versionCode` equal the repository (`tool/verify_artifact.sh matrix`, `pubspec.yaml`); every provider authority starts with the application ID; not debuggable; cleartext traffic and backups off; `targetSdk` at least 36 (Google Play) |
| APK signature | `apksigner` verifies; schemes v2 and v3 present; exactly one signer |
| AAB signature | `jarsigner` verifies and no entry lies outside the signature; exactly one signer; certificate valid beyond 2033-10-22 |
| Signer | SHA-256 equals the expected upload fingerprint; not a debug certificate; not an identity in `do_not_use`; not the Play app-signing certificate (no local build can hold it). Classified `release-local`, `play-signed`, `debug` or `unknown` |
| Native code | Exactly the ABIs `arm64-v8a`, `armeabi-v7a`, `x86_64`; `libflutter.so` and `libapp.so` present; `libdlcplazacryptlib.so` and the `libsecp256k1_zkp` library are byte-identical to `config/release/native_libs.json` (the stripped, shipped form; the unstripped inputs are the committed `jniLibs`) |
| 16 KB pages | Every 64-bit library has ELF `PT_LOAD` alignment of at least 16 KB; an APK is also zip-aligned for 16 KB pages (`zipalign -P 16`). 32-bit libraries are not subject to the requirement |
| Pair | The APK and the AAB agree on ID, name, versions, signing certificate and every native library |
| Provenance | `release` only: commit, clean tracked tree, configuration digest, ledger digests, toolchain, production gate |

Subcommands: `apk`, `aab`, `pair`, `release`. Usage errors and unreadable artifacts exit 2;
a failed check exits 1; an artifact is never passed because something could not be read.
`tool/verify_artifact.sh` stays the lightweight CI check of validation builds (debug-signed);
`verify_android_release.py` is the release check and refuses a debug-signed artifact.

**Not verified:** that Google Play accepts the upload, what Play signs delivered APKs with
(only Play Console shows it), anything about a device, the identity of the key holder.

## 4. The local procedure

Preconditions: a clean checkout of the **committed** release commit; JDK 17 (`JAVA_HOME`,
and `flutter config --jdk-dir` pointing at it); `ANDROID_HOME`; Flutter 3.35.3; the pinned
bundletool (`curl -fsSLO https://github.com/google/bundletool/releases/download/1.18.3/bundletool-all-1.18.3.jar`;
SHA-256 `a099cfa1543f55593bc2ed16a70a7c67fe54b1747bb7301f37fdfd6d91028e29`, checked by the script);
the keystore and a properties file with `storeFile` and `keyAlias` outside the repository; and
a build number above the published one (the production gate refuses otherwise).

```bash
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64   # your JDK 17
export ANDROID_HOME=$HOME/Android/Sdk
export BUNDLETOOL_JAR=$HOME/tools/bundletool-all-1.18.3.jar
read -rs CADENA_KEYSTORE_PASSWORD; export CADENA_KEYSTORE_PASSWORD
read -rs CADENA_KEY_PASSWORD;      export CADENA_KEY_PASSWORD
tool/release_android.sh \
  --signing-properties ~/cadena-signing/signing.properties \
  --expect-cert-sha256 <SHA-256 of the upload certificate> \
  --identity-label "CadenaBitcoin upload key <year>" \
  --out ~/cadena-releases/<version>
```

What it does, in order, and stops at the first problem: refuses (exit 2, nothing built) when a
precondition is missing, the tracked tree is dirty, `tool/verify_version.sh` fails or the
production gate (`tool/build_manifest.py gate`) fails; builds the production APK and AAB with
`CADENA_SIGNING=release`; copies them to `--out` as
`cadena-signer_production_<version>_<commit7>_local-signed.apk` and `..._upload-signed.aab`;
runs `verify_android_release.py release`, which writes `release-report.json`,
`release-report.md` and `SHA256SUMS` next to them. Exit 0 means built, signed, verified and
recorded; the report says `RELEASE READY (verified, NOT published)` and `distributable: false`.

The release report is the audit record: commit, version, configuration, ledgers, toolchain,
host, the SHA-256 and signer of each artifact, all checks with their results, the production
gate output and what is not verified. Keep it with the artifacts; a release is reproducible
from the commit and the report, apart from the signature (a signature is not reproducible
byte-for-byte, so compare the unsigned content through the native-library hashes and the
version evidence, not the artifact hash).

## 5. After Google has activated the new upload key

> Steps 1-5 were carried out for release 1.0.4+1000035 (record in section 9). Steps 6 and 7 are
> only partly recorded there. The procedure stays here as the checklist for the next release.

1. In Play Console (App integrity / App signing), read the **upload key certificate** SHA-256 and
   check that it equals the fingerprint of the new key
   (`keytool -list -v -keystore <keystore> -alias <alias>`, SHA256 line). Do not continue if
   they differ. The **app signing key certificate** must still be `13:52:D9:EE:…:AC:9F:CB`.
2. Record the upload fingerprint in `config/release/android_signing.json` (`upload.active_sha256`)
   by a reviewed pull request. From then on the tools refuse an `--expect-cert-sha256` that differs.
3. Raise the version by a reviewed commit (`pubspec.yaml`; the `versionCode` must exceed 1000034,
   which the production gate enforces; the product version is a release-authority decision).
4. Build, sign, verify and record with `tool/release_android.sh` (section 4) on the release commit.
   Read the report. Proceed only with `RELEASE READY`.
5. Upload the `.aab` to Google Play Console (a separate, explicitly authorized step; start with an
   internal testing track). Google checks the signature against the upload key and re-signs with the
   app-signing key.
6. After processing, check in Play Console that the app signing key certificate is unchanged and,
   for a Play-signed APK you downloaded, verify it:
   `python3 -I tool/verify_android_release.py apk production <file.apk> --signing play`.
7. Record the delivery (channel, date, who authorized it) with the report. Website delivery of an
   APK is its own authorized step; see the consequence in section 1.

To create the upload key and ask Google to replace the old one is the CFO's task (key generation,
the exported certificate, the reset request in Play Console). The key and the passwords never enter
this repository, a chat, a ticket or a log.

## 6. Failure modes

| You see | Meaning |
|---|---|
| `CADENA_SIGNING=release, but the signing credentials are incomplete. Missing: …` | A property or environment variable is absent; nothing was signed |
| `The signing certificate does not match the expected one` | Wrong keystore, wrong alias or wrong `--expect-cert-sha256`; nothing was signed |
| `must be outside the repository directory` | Move the keystore or the properties file |
| `CADENA_SIGNING must be unset, 'validation' or 'release'` | A typo; there is no guessing |
| `the production release gate fails` | The build number is not above the published one, or the application ID is not the published package |
| `signed with a DEBUG certificate` | A validation-mode artifact was offered as a release |
| `NOT 16 KB aligned` / `differs from config/release/native_libs.json` | The build changed the native libraries; a reviewed change of the ledger and the libraries is needed |
| `NOT READY` with a good verification | The tracked tree was dirty or the gate failed; see `not_ready_reasons` in the report |

## 7. Tests

`tool/test_android_release.sh` (always: static checks of the Gradle file and the ledgers, unit
tests of the ELF and fingerprint code, the driver's refusals; with `REAL_APK` and `REAL_AAB`: the
verifier on real artifacts re-signed with disposable keys, positive and negative, and the release
report; with `ANDROID_RELEASE_E2E=1`: the whole procedure with real builds).

`tool/test_android_gradle_signing.sh` runs the signing rules in **real Gradle** (`--dry-run`: the project is
configured and the task graph built, nothing is compiled, signed or written; seconds per case): validation
mode builds every flavor, `release` mode plans production and refuses every staging release task and the
flavor-less aggregates, and the fail-closed refusals (typo, no credentials, wrong certificate, wrong
password) still hold. It creates its own disposable keystore. Run against the Gradle file without the
production-only rule, nine of its cases fail.

**In CI.**
- **On pull requests:** `.github/workflows/android-release-tests.yml` runs `test_android_release.sh`
  (hermetic part), `verify_version.sh`, `test_release_versioning.sh` and `test_android_gradle_signing.sh`
  on every pull request to `development`, `staging` or `production` (and on a manual run), with no path
  filter. It builds nothing, signs nothing, uploads nothing and holds no secret; the only key is the
  disposable one a test creates on the runner. It is a separate workflow because `build-variants.yml`,
  the release/promotion workflow, deliberately never starts from a pull request
  (docs/RELEASE_TRIGGERS.md). The tests pin the shape of this workflow (triggers, read-only permissions,
  no secret, no build, pinned actions).
- **On promotion:** the `plan` job of `build-variants.yml` also runs the hermetic part, on a push to
  `staging` or `production` and on a manual run.
- **Not in CI:** the tests that need real artifacts and a disposable key (`REAL_APK`/`REAL_AAB`) and the
  end-to-end procedure (`ANDROID_RELEASE_E2E=1`) run locally, before a release or when the signing, the
  verifier or the native libraries change.
- No workflow signs, holds a key or secret, runs `tool/release_android.sh` or uploads to Google Play; a
  test pins exactly that.

## 8. Known limitations

- No CI job signs, and none runs the tests that use real artifacts or the end-to-end procedure (section 7).
  Whether the pull-request checks are required for merging is a repository-ruleset decision, not made here.
- The release tools still need `--expect-cert-sha256` explicitly. The active upload fingerprint is
  recorded in `config/release/android_signing.json` and the tools refuse a different value, but a
  release verification never takes the expectation from the ledger alone.
- There is no Android staging signing identity. `release` is production-only and Gradle enforces it
  (section 2); a staging build is debug-signed validation only. A staging identity would be a separate,
  reviewed design.
- The pinned native-library hashes are those of the stripped form made by NDK 27.0.12077973; another NDK may
  strip differently and need a reviewed ledger change.
- The production gate now fails for the repository's own version: `pubspec.yaml` is at the published
  1.0.4+1000035, and a build number is never reused. The next production release needs a reviewed
  version bump above 1000035 (`config/release/published_versions.json`).
- What Google Play signs delivered APKs with, and whether the website APK is the locally signed or the
  Play-signed one, are outside this repository (section 1).
- Not established, and tracked outside this document: official Android **staging** signing and its
  internal distribution (section 2 and the bullet above); whether the **website APK** is the locally
  signed or the Play-signed one (section 1); whether production signing stays **local** or moves to a
  protected CI environment (no decision has been made; no workflow signs); **credential custody,
  backup, recovery and succession** (Issue #66); **controlled retention and handover** of the signed
  artifacts and the release report (section 9: they exist on the build workstation only).
