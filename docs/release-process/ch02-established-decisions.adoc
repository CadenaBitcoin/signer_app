= Register of established decisions
:description: Established architectural and operational decisions, their origin, implementation status and supporting evidence.

*Scope:* Decisions already made, their implementation status, supporting evidence and necessary documentation reconciliation.

*Status:* Adopted (revision 4). Decisions are authoritative; the implementation status of each is stated in its row and in `STA-01`.

This register records established architectural and operational decisions.

A distinction is maintained between:

* *Decided:* A requirement or architectural principle approved by the CTO.
* *Implemented:* A mechanism that exists in the current system.
* *Verified:* An implemented mechanism whose behavior has been demonstrated by appropriate evidence.

An approved decision does not imply that its implementation exists or has been verified.

Where older documents contradict a later approved decision, the documentation must be reconciled.

Where an approved decision changes existing system behavior, the current implementation remains authoritative until the reviewed implementation change takes effect.

| DEC-28
a| *Sole Apple credential-management sequence.*

The following sequence applies to both staging and production iOS delivery:

. Complete all checks establishing that the promotion pull request is ready to merge.
. Upload the three temporary Apple credentials using the local operator-controlled credential-management script.
. Verify that all three credentials are present.
. Merge the approved promotion pull request.
. Approve the protected signing job.
. Establish that the delivery workflow has finished and verify its outcome.
. Remove the temporary credentials, regardless of whether delivery succeeded, failed or was cancelled.
. Verify that all three credentials are absent.

Uploading credentials after the promotion merge is not a supported alternative.

An abandoned or interrupted delivery must be brought to a safe conclusion, including cancellation where necessary and verified credential removal.

Temporary credentials must not remain provisioned indefinitely while waiting for an operator action.
| UNR-03: approved.

xref:ch08-operator-credential-tool.adoc#ch08[Chapter 8].

`CRD-04`, `CRD-07`, `CRD-08`, `CRD-09`.

The sequence has been demonstrated manually. The operator tool and interruption-handling mechanisms remain to be implemented and verified.

| DEC-29
| *Release identification.*

The separate release candidate counter `rc.N` is eliminated.

The application version and numerical build number provide the authoritative version information.

Git commit hashes and the associated build evidence identify the exact source used for a build.

Git tags are not required as an independent version identification or release authorization mechanism.

Automatically generated tags are permitted where required for GitHub Releases. They must be derived from existing authoritative information, introduce no independent version counter and require no routine manual administration.

Existing historical tags, where present, are preserved.
| UNR-04: resolved in principle.

`VER-07`.

| DEC-30
a| *Build-number encoding.*

The numerical build number encodes the application version and development revision using the structure `XX.YY.ZZ.RRR`.

Starting from the least significant decimal digit:

* Three digits represent the development revision.
* Two digits represent the patch version.
* Two digits represent the minor version.
* The remaining digits represent the major version.

For example, application version `2.1.34`, revision `65`, produces numerical build number `20134065`.

The proposed encoding must be verified against platform limits, historical build-number constraints and overflow conditions before implementation.
| UNR-05: resolved in principle.

xref:ch11-build-and-release-architecture.adoc#ch11[Chapter 11].

`VER-08`.

No concrete incompatibility has been established. Complete platform compatibility remains to be verified.

| DEC-31
a| *One version sequence.*

There shall be one shared numerical build-number allocation sequence.

There shall be no independently maintained:

* Platform-specific build-number counter.
* Environment-specific build-number counter.
* Release candidate counter.
* Duplicate authoritative version counter.

Subsequent delivery operations inherit version information rather than independently generating it.

Version information is extracted from the applicable application artifacts and verified against durable build evidence.
| `VER-09`, `VER-12`, `VER-15`.

| DEC-32
a| *Magic: manually triggered Android staging build.*

Magic is the manually initiated Android build operation originating from `development`.

Magic performs the following operations:

. Determines the applicable application version.
. Allocates and persistently records a new numerical build number.
. Builds an Android APK using the staging application identity and configuration.
. Verifies the resulting artifact.
. Preserves the successful APK and its build evidence.

Magic is the sole routine mechanism that increments the development revision counter.

It may be executed as frequently as required during development, independently of branch promotions.

Every allocated build number is consumed. A failed or interrupted invocation must not make an allocated number available for reuse.

The APK generated by Magic is the staging APK. There is no separate routine DEV APK delivery mechanism.
| xref:ch11-build-and-release-architecture.adoc#ch11[Chapter 11].

`VER-10`, `VER-11`.

WP-C1.

The underlying APK build mechanism should be consolidated from existing implementations wherever practicable.

| DEC-33
| *Development-to-staging promotion.*

A reviewed merge from `development` into `staging` automatically initiates iOS staging delivery.

It does not generate another Android staging APK for delivery.

The delivery operation identifies the applicable successful Magic build and retrieves its application version and numerical build number from the APK, verified against its build evidence.

The application source used to generate the APK is compared with the application source being promoted.

Any relevant source discrepancy must be detected, reported and preserved in the delivery evidence.

The CTO accepts that the Android and iOS staging applications may share the same application version and build number while containing different application source revisions.

Source differences alone do not prohibit staging delivery.

No build-number increment occurs during the promotion.

The association between the Android build, promoted source, iOS delivery and inherited version information must remain retrievable.
| xref:ch11-build-and-release-architecture.adoc#ch11[Chapter 11].

`DEL-05`, EXC-13.

WP-C2.

The implications of staging source discrepancies for subsequent production authorization remain subject to UNR-06.

| DEC-34
a| *Staging-to-production promotion.*

A reviewed and authorized merge from `staging` into `production` initiates production delivery.

The production delivery generates:

* Production Android APK.
* Production Android AAB.
* Production iOS application.

All production artifacts must originate from the same approved application source and carry identical inherited application version and numerical build-number information.

Environment-specific configuration, platform-specific implementation and signing differences remain expected.

The production delivery inherits the version information established by the specifically identified and accepted staging delivery.

The current development version counter is not consulted as an authority for production version selection.

No build-number increment occurs during production promotion.

Production publication remains subject to the applicable release authorization, security, validation and distribution requirements.
| xref:ch11-build-and-release-architecture.adoc#ch11[Chapter 11].

xref:ch10-production-extensions.adoc#ch10[Chapter 10].

UNR-09.

| DEC-35
a| *Persistent artifact availability and durable build records.*

Following the initial successful publication, a production APK must remain persistently and publicly downloadable.

GitHub Releases is the preferred production APK distribution mechanism.

Staging APKs must also have persistent storage. Their access and distribution policy is decided separately.

An existing successfully published APK remains available until its replacement has been successfully built, verified and published.

Failed, interrupted or cancelled builds must not remove or replace the existing available APK.

Expiring GitHub Actions artifacts alone are insufficient for persistent application distribution or durable release evidence.

Machine-readable build records must enable subsequent workflows to retrieve and verify:

* Application version.
* Numerical build number.
* Source commit or equivalent source identity.
* Application environment.
* Artifact checksum.
* Build outcome.
* Corresponding workflow execution.

Production delivery must identify the specific accepted staging delivery rather than selecting an arbitrary latest artifact.

The storage and protection mechanisms for durable build records remain subject to technical investigation.
| xref:ch11-build-and-release-architecture.adoc#ch11[Chapter 11].

`DEL-07`, `EVD-05`.

WP-C3.

| DEC-36
a| *Build-trigger matrix.*

The approved delivery architecture consists of three principal operations:

* Magic, manually initiated from `development`: builds the staging APK and increments the build number.
* Development-to-staging promotion: builds and delivers the staging IPA without incrementing the build number.
* Staging-to-production promotion: builds the production APK, AAB and IPA without incrementing the build number.

Credential-free compilation, static analysis, regression testing and other validation operations remain separate from application delivery and may run automatically.
| xref:ch11-build-and-release-architecture.adoc#ch11[Chapter 11] contains the authoritative build-trigger matrix.

`DEL-01`.

| DEC-37
| *Historical build-number initialization.*

Magic must be initialized in a manner that prevents allocation of any previously consumed build number.

Initialization must account for relevant historical Android and iOS builds, including published builds, uploaded builds, failed delivery attempts and attempts whose outcome is indeterminate.

Previously consumed numbers such as `10005001` and `10005002` must not be allocated again.

A complete historical inventory is an acceptable initialization mechanism but is not mandatory where a trustworthy upper boundary for previously consumed numbers can be established instead.

Any such boundary must account for all relevant application identities, the shared allocation sequence, platform monotonicity requirements and the approved build-number encoding.

Magic must refuse to allocate a number when safe initialization cannot be established.

The objective is reliable non-reuse of consumed numbers, not exhaustive reconstruction of historical build activity for its own sake.
| CTO clarification of 2026-11-27; acceptance audit F-01; Chapter 2 review.

`VER-13`, `VER-14`.

WP-C1, FQ-12.

| DEC-38
| *Single source of truth and derived version information.*

The application version and numerical build number must form one unambiguous, authoritative version declaration for each build.

Magic is responsible for establishing and persistently recording the newly allocated build number.

Subsequent delivery operations inherit the version information associated with the specifically identified preceding build or delivery.

Application artifact fields, authorization records, delivery records, user interface displays and historical evidence may contain derived copies of authoritative version information.

Such copies do not constitute independent sources of truth, provided that they are derived from or verified against the authoritative build information and cannot independently redefine it.

No independently maintained duplicate version declaration or counter is permitted.

The authoritative application version and allocation information may reside in one file or in coordinated storage structures, provided that their relationship is unambiguous and securely enforced.

The exact storage mechanism, including the future role of `pubspec.yaml` and its build-number component, remains subject to technical investigation.

No implementation-specific storage arrangement is established by this decision.

== Reconciliation of current and target architecture

The current implementation and the approved target architecture must remain explicitly distinguishable throughout the documentation.

Until the target architecture takes effect:

* The authoritative version information is obtained from the existing `pubspec.yaml` mechanism.
* The development-to-staging promotion retains its existing Android and iOS delivery behavior.
* The existing authorization and verification mechanisms remain in force.
* Build-number consumption and delivery recovery follow the existing operational procedure.

After the reviewed implementation change establishing the target architecture:

* Magic becomes the sole routine build-number allocation mechanism.
* Magic becomes the sole routine staging APK delivery mechanism.
* Development-to-staging promotion delivers the iOS staging application using inherited version information.
* Staging-to-production promotion inherits the accepted staging version information and generates the production artifacts from a consistent application source.

There must be no transitional period during which multiple independent mechanisms are simultaneously authoritative for build-number allocation or selection.

The implementation sequence and conditions for changing from the current architecture to the target architecture are defined in xref:ch09-migration-sequence.adoc#ch09[Chapter 9].
