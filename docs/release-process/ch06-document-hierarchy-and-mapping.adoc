[[ch06]]
= AsciiDoc documentation hierarchy and migration
:description: The target documentation structure, the responsibilities of its individual parts and the migration of existing documentation.

*Scope:* The organization of authoritative human-oriented documentation, its relationship to machine-readable information, and the migration of existing repository documents.

*Status:* Proposal for review. No repository document has been moved or replaced through this specification.

== Objectives

The documentation architecture must support:

* Independent development and maintenance of individual documents.
* Inclusion of individual documents in a comprehensive documentation book.
* Unambiguous identification of authoritative requirements.
* Understandable architectural reasoning.
* Practical operational procedures.
* Reconstruction of the release infrastructure independently of a particular developer, assistant or workstation.
* Preservation of historical decisions and release evidence.
* Minimal duplication and administrative overhead.

The documentation must be useful to both human developers and AI-assisted development tools.

It must not depend on access to previous conversations or undocumented personal knowledge.

== Documentation principles

=== Canonical format

Native AsciiDoc is the canonical format for human-oriented documentation (DEC-25).

Machine-readable files retain the format required by their consuming tools.

Externally prescribed or tool-specific documents may retain Markdown or another required format.

Such documents should reference authoritative AsciiDoc content rather than maintain independent copies of normative requirements.

=== One authoritative location

Every normative requirement has one authoritative definition.

Other documents may reference, explain or operationally apply that requirement, but must not independently redefine it.

The different documentation categories have distinct responsibilities:

[cols="2,4",options="header"]
|===
| Category | Responsibility

| Governance
| Authority, responsibilities, contribution rules and repository governance.

| Policy
| Normative architectural, operational and security requirements.

| Architecture
| System structure, design decisions, rationale and component relationships.

| Implementation
| Implemented mechanisms, workflows, tools and verification procedures.

| Infrastructure
| External services, required configuration and reconstruction information.

| Operations
| Practical procedures for performing authorized operations.

| Current state
| Implementation status, outstanding work and applicable exceptions.

| Records
| Historical decisions, delivery outcomes and supporting evidence.

| Archive
| Superseded designs and historical material without current normative authority.
|===

A runbook may repeat information necessary for safe execution.

Such repetition is an operational representation of an authoritative requirement, not a separately maintained policy.

=== Independent and includable documents

Each substantive documentation page should have:

* A descriptive title.
* A stable anchor.
* A clearly identifiable scope.
* An implementation or approval status where applicable.
* References to related authoritative documents.

Individual pages must remain understandable when read independently.

They must also be suitable for inclusion in the master documentation book.

Cross-references use stable anchors and appropriate native AsciiDoc mechanisms.

The implementation must verify that cross-references work both when rendering individual documents and when rendering the complete book.

Directory structure alone must not be relied upon to establish document authority.

=== Appropriate modularity

Documentation is divided according to meaningful responsibilities.

A separate document is justified when its subject:

* Has an independent architectural or operational purpose.
* Has a distinct maintenance lifecycle.
* Is independently referenced or consumed.
* Would otherwise make a larger document unnecessarily difficult to maintain.

Closely related subjects may remain in one document.

A small requirement group does not automatically require a separate file.

The proposed hierarchy is an organizational framework, not a mandatory file count.

=== Separation of documentation and operational data

Machine-consumed authorization and release information belongs in suitable machine-readable structures.

Human-oriented documentation explains their meaning and operational use.

Reorganizing narrative documentation should not unnecessarily require changes to release gates or other security-critical implementation files.

See xref:ch07-machine-readable-state.adoc#ch07[Chapter 7].

=== Security-critical implementation references

Authorization-bound workflows, gates and tools should avoid unnecessary dependencies on incidental documentation paths or wording.

Stable requirement identifiers may be used to establish traceability.

Useful documentation references are not prohibited merely because they occur in an implementation file.

Operationally necessary references remain applicable.

Any change to an authorization-bound file follows the corresponding reviewed change procedure.

See `DOC-04` and xref:ch09-migration-sequence.adoc#ch09[Chapter 9].

=== Historical traceability

Superseded requirements and architectural decisions remain retrievable where they provide meaningful historical context.

Historical material must be clearly distinguishable from current normative documentation.

Git history remains part of the project's historical record.

Archiving a superseded document is useful where retaining it improves understanding, reconstruction or auditability.

There is no requirement to maintain redundant copies of every previous document.

== Responsibilities of the documentation parts

=== Front matter

The front matter establishes the purpose and scope of the documentation.

It contains terminology, reading guidance and documentation conventions.

Terminology should be defined centrally where its meaning applies across multiple documents.

=== Governance

Governance documents establish:

* Repository authority and responsibilities.
* Branch management and promotion rules.
* Contribution and review requirements.
* Security reporting.
* AI-assisted development constraints.

Root-level entry points remain available where required by external tools or contributor discovery conventions.

=== Policy

Policy documents contain normative requirements.

They establish what the infrastructure must guarantee without unnecessarily prescribing unresolved implementation mechanisms.

Stable requirement identifiers provide traceability between policy, implementation and verification.

Requirements defined in xref:ch05-requirements-and-enforcement.adoc#ch05[Chapter 5] and xref:ch10-production-extensions.adoc#ch10[Chapter 10] are incorporated into their appropriate authoritative locations.

The migration must explicitly establish whether a requirement matrix or an individual policy page is the authoritative definition of each requirement.

Both must not be maintained as independent normative authorities.

=== Architecture

Architecture documents explain how the system is organized and why its principal decisions were made.

They establish the relationship between:

* Magic.
* Application version management.
* Environment configuration.
* Branch promotions.
* Authorization.
* Application compilation.
* Signing and verification.
* Artifact distribution.
* Durable build evidence.

Architecture documents must distinguish established architectural requirements from candidate implementation mechanisms.

The build-trigger matrix defined in xref:ch11-build-and-release-architecture.adoc#ch11[Chapter 11] has one authoritative definition.

Related architecture and operational documents reference that definition.

=== Implementation

Implementation documentation explains the mechanisms satisfying the architectural and policy requirements.

It identifies relevant:

* Workflows.
* Scripts and tools.
* Configuration files.
* Authorization gates.
* Verification procedures.
* Automated tests.
* Authorization-bound implementation files.

The requirement-to-enforcement matrix identifies the relationship between requirements and mechanisms.

A generated matrix may be introduced where this reduces duplication.

Generation is not mandatory if a simpler maintained representation provides sufficient traceability.

Implementation status must remain consistent with the maintained current-state documentation.

=== Infrastructure

Infrastructure documentation provides the information necessary to understand, verify and reconstruct external release infrastructure.

It covers the applicable GitHub, Apple and Google Play arrangements.

It distinguishes between:

* Required configuration.
* Observed external configuration.
* External identifiers.
* Required permissions.
* Credential references.
* Human-controlled prerequisites.

Credential values and private signing material are not included.

The reconstruction documentation must not depend on the availability of a particular workstation or undocumented local setup.

=== Operations

Operational documentation contains procedures that can be followed by an appropriately authorized operator.

The procedures should identify:

* Prerequisites.
* Required authority.
* The sequence of operations.
* Expected results.
* Failure and interruption behavior.
* Required closeout and evidence.

Operational documents should remain concise and actionable.

They must not require an operator to reconstruct the intended procedure from several independent architectural documents.

The approved Apple credential-management sequence is defined by DEC-28 and xref:ch08-operator-credential-tool.adoc#ch08[Chapter 8].

The local operator tool is distinguished from the manual procedure until its implementation has been verified.

=== Current state

The current-state documentation distinguishes implemented and verified behavior from approved but unimplemented requirements.

`STA-01` identifies the principal maintained as-built overview.

The current-state documentation includes or references:

* Implemented release mechanisms.
* Outstanding implementation work.
* Verification limitations.
* Applicable temporary exceptions.
* Unresolved architectural decisions.

GitHub issues and other established work-management mechanisms remain authoritative for their actual issue state.

The documentation should reference those records rather than introduce an independently maintained duplicate task-management system.

Historical release facts remain in delivery records.

They are not rewritten whenever the current system state changes.

=== Records

Release records preserve the evidence of particular operational events.

They may contain:

* Release authorization references.
* Application versions and numerical build numbers.
* Source identities.
* Workflow execution identifiers.
* Artifact identities and checksums.
* Delivery outcomes.
* Human-reported observations.
* Accepted limitations and exceptions.

Human-oriented release records do not replace authoritative machine-readable build evidence.

See DEC-23, DEC-35 and xref:ch07-machine-readable-state.adoc#ch07[Chapter 7].

=== Archive

The archive contains material retained primarily for historical understanding.

Archived documents must be clearly identified as historical and non-normative.

An archived document must not remain an active machine-readable authorization source.

== Migration of existing documents

=== Migration inventory

Before moving, splitting or retiring an existing document, identify:

* Human-oriented references.
* External links and contributor entry points.
* Workflow and script references.
* Machine-readable dependencies.
* Automated test dependencies.
* Authorization-bound implementation dependencies.
* Existing uncommitted user changes.

Classify each dependency according to its actual operational purpose.

An incidental reference does not necessarily require retention of the original document indefinitely.

A machine-readable dependency must be migrated before its source can be removed.

=== Reference compatibility

Where an existing document has moved but its previous location remains referenced, preserve a short compatibility stub where practical.

A compatibility stub contains:

* A short identification of the original document.
* A statement that its authoritative content has moved.
* A reference to the replacement document or section.

A stub is not a second authoritative document.

It must not preserve superseded normative requirements merely for convenience.

Where the old document is consumed by a machine, a stub alone is insufficient.

The consumer must be migrated and tested before replacing its operational input.

Root-level entry points required by external tools may remain permanent rather than temporary stubs.

=== Authorization-bound dependencies

References within authorization-bound implementation files are reconciled through the applicable reviewed change procedure.

Such files must not be changed incidentally during a documentation-only migration.

The corresponding authorization state, implementation bindings and security tests must remain valid.

See xref:ch09-migration-sequence.adoc#ch09[Chapter 9].

=== Automated test dependencies

Tests that depend on incidental narrative wording or current operational state should be reconciled with the underlying requirement.

Existing tests must not simply be removed because documentation has moved.

Distinguish between:

* Security and operational behavior tests.
* Machine-readable schema validation.
* Historical evidence preservation tests.
* Documentation structure and reference checks.

Each applicable property remains verified after migration.

=== Historical preservation

Historical release evidence must remain attributable to its original source and operational event.

Format conversion or document relocation must not silently change historical facts.

Where necessary, retain the original commit, record identifier or historical reference.

Any substantive historical correction must be explicitly identified.

=== Retirement of old paths

An old document path may be retired when:

* No required machine consumer depends on it.
* Applicable automated tests have been reconciled.
* Relevant internal references have been updated.
* External entry-point requirements remain satisfied.
* Historical evidence remains retrievable.

A permanent compatibility entry point may remain where external references cannot reasonably be updated.

== Master documentation book

The master documentation file is:

[source,text]
----
docs/index.adoc
----

It includes the applicable documentation parts in their intended reading order.

The master document should define common book-level attributes where appropriate, including:

* Document type.
* Table of contents.
* Section numbering.
* Common presentation attributes.
* Include conventions.

Individual pages must remain suitable for standalone rendering.

Common content must not be duplicated merely to support standalone and book rendering.

The documentation structure must be tested for:

* Successful standalone rendering.
* Successful rendering of the complete documentation book.
* Correct section hierarchy.
* Unique anchors within the assembled book.
* Resolvable cross-references.
* Correct include paths.
* Correct rendering of tables and source blocks.

Successful structural inspection of AsciiDoc source is not equivalent to successful rendering.

The framework must be rendered with Asciidoctor before documentation adoption.

PDF generation may be supported where useful but is not required to establish the canonical documentation format.

The native AsciiDoc source remains authoritative.

== Migration sequence

Documentation migration is coordinated through WP-B1, WP-B2, WP-B3 and the applicable supporting implementation work packages.

The general sequence is:

. Establish the documentation conventions and target organization.
. Reconcile misleading implementation-status statements.
. Identify authoritative requirements and their target locations.
. Resolve machine-readable dependencies and authorization-bound references through the applicable reviewed changes.
. Migrate human-oriented documentation.
. Preserve historical records and necessary compatibility entry points.
. Validate references, includes and rendering.
. Retire redundant documents when their dependencies have been resolved.

The migration does not require immediate creation of every proposed document.

Documentation parts may be migrated independently where their dependencies permit it.

The exact implementation sequence is governed by xref:ch09-migration-sequence.adoc#ch09[Chapter 9].

== Acceptance criteria

The documentation migration is accepted when:

* Human-oriented documentation uses native AsciiDoc as its canonical format.
* Each normative requirement has one identifiable authoritative location.
* Current implementation is distinguishable from approved target architecture.
* Individual documents render independently.
* The complete documentation book renders successfully.
* Cross-references and document includes resolve correctly.
* Machine-readable operational dependencies remain functional.
* Existing authorization and verification guarantees remain intact.
* Historical decisions and release evidence remain retrievable.
* Required external and tool-specific entry points remain functional.
* Existing uncommitted user changes have been preserved.
* Redundant normative documentation has been eliminated.
* The resulting structure is understandable without access to previous assistant conversations or undocumented workstation-specific knowledge.

Acceptance is based on the usability, consistency and integrity of the documentation.

The number of files, directories or pages is not an acceptance criterion.
