[[ch08]]
= Credential management and operator tool
:description: The approved Apple credential-management sequence, the operational procedure and the specification of the local operator-controlled tool.

*Scope:* Temporary Apple delivery credentials, their provisioning and removal, the responsibilities of the operator, and the supporting local tool.

*Status:* The credential-management sequence is approved through DEC-28 and UNR-03. The local operator tool remains to be implemented and verified (WP-A1, `CRD-05`).

This chapter defines the operational procedure.

It does not authorize a delivery, provision credentials or contain credential values.

== Terminology

[cols="2,4",options="header"]
|===
| Term | Meaning

| Promotion pull request
| The reviewed pull request that merges `development` into `staging` or `staging` into `production`.

Its merge initiates the corresponding delivery workflow.

| Delivery workflow
| The automatic GitHub workflow responsible for building, verifying, signing and delivering the authorized application artifacts.

| Signing job
| The protected workflow job responsible for Apple signing and delivery operations requiring temporary Apple credentials.

| GitHub environment
| The environment configuration that restricts deployment branches, requires human approval and provides the applicable environment secrets.

| Temporary credentials
| The three Apple credential values temporarily provisioned into the designated GitHub environment.

| Operator
| The authorized person responsible for credential provisioning, delivery supervision and credential removal.

| Maintainer
| The person authorized to merge the approved promotion pull request.

| Environment reviewer
| The person authorized to approve the protected signing job.
|===

The operator, maintainer and environment reviewer may be the same individual acting in different authorized roles.

Their separation into operational roles does not establish independent review (DEC-16, EXC-08).

== Credential scope

The existing Apple delivery procedure uses three designated GitHub secrets:

* `APPLE_API_KEY_P8`
* `APPLE_API_KEY_ID`
* `APPLE_API_ISSUER_ID`

The currently established GitHub environments are:

[cols="2,3",options="header"]
|===
| Application environment | GitHub signing environment

| Staging
| `ios-hosted-signing-stg`

| Production
| `ios-hosted-signing`
|===

The credentials must be provisioned exclusively into the environment corresponding to the authorized delivery.

They must not be provisioned at repository, organization or Dependabot scope.

The three designated credentials must be absent from GitHub when no authorized delivery operation requires them.

This requirement concerns the designated Apple delivery credentials.

It does not prohibit unrelated secrets required by other explicitly authorized mechanisms.

The current Apple key is an Admin-role App Store Connect team API key.

Its long-term custody, privileges, recovery, rotation and revocation remain subject to UNR-02.

== The sole credential-management sequence

The following sequence applies to both staging and production Apple delivery (DEC-28).

No alternative procedure involving credential provisioning after the promotion merge is supported.

[cols="1,5,2",options="header"]
|===
| Step | Operation | Responsibility

| 1
| *Establish readiness.*

Complete all applicable pre-promotion checks.

The promotion pull request must be approved and ready to merge.

The authorization, application source, inherited version information, implementation bindings, CI checks, environment protection and distribution prerequisites must satisfy the applicable requirements.

No conflicting delivery operation may be waiting or running.

The three designated Apple credentials must be absent.
| Operator.

| 2
| *Provision credentials.*

Upload the three designated Apple credentials into the applicable GitHub signing environment using the local operator-controlled tool.
| Operator.

| 3
| *Verify presence.*

Confirm that all three designated credentials are present in the intended environment and absent from prohibited scopes.

Do not merge unless verification succeeds.
| Operator, supported by the tool.

| 4
| *Merge the promotion pull request.*

Merge the specifically approved and verified pull request.

The merge initiates the corresponding delivery workflow.
| Maintainer.

| 5
| *Approve the protected signing job.*

Approve the signing job associated with the authorized delivery.

Verify that the approval concerns the intended workflow execution and application environment.
| Environment reviewer.

| 6
| *Verify the delivery outcome.*

Wait for the workflow to conclude.

Inspect the applicable job results, artifact verification evidence and Apple upload confirmation.

Distinguish successful delivery, failure, cancellation and indeterminate outcomes.
| Operator.

| 7
| *Remove credentials.*

Remove the three temporary Apple credentials regardless of the delivery outcome.
| Operator.

| 8
| *Verify absence.*

Confirm that the three designated Apple credentials are absent from both signing environments and all applicable prohibited scopes.
| Operator, supported by the tool.
|===

The credential exposure period begins when the first credential is successfully provisioned and ends when the last credential is removed.

The procedure is complete only after credential absence has been verified.

=== Failure before the promotion merge

If readiness cannot be established, credentials must not be provisioned.

If provisioning has begun but readiness changes, provisioning fails or the promotion is abandoned:

. Do not merge the pull request.
. Remove any designated credentials already provisioned.
. Verify their absence.

The promotion may subsequently proceed through a new execution of the approved sequence, provided that its authorization remains valid.

=== Failure after the promotion merge

If delivery fails or must be abandoned:

. Establish the current workflow state.
. Cancel the workflow where necessary.
. Establish that the workflow has concluded, where possible.
. Remove the temporary credentials.
. Verify their absence.
. Record the delivery outcome.
. Apply the applicable authorization withdrawal and recovery procedure.

Credential removal must not be postponed indefinitely because workflow termination cannot be confirmed.

Removing a GitHub environment secret does not necessarily remove credentials already loaded into an executing job.

Cancellation and credential removal are therefore separate operations.

Recovery of the failed application delivery is also separate from credential cleanup.

The existing staging recovery procedure remains governed by DEC-13 and DEC-24.

Partial production delivery remains subject to UNR-09.

=== Rationale for the sequence

Provisioning before the merge establishes credential readiness before the automatic delivery starts.

The operator does not need to interrupt a waiting delivery workflow to provision its credentials.

The credentials remain available only for the period necessary to execute the authorized operation.

No additional provisioning order is introduced.

== Operator-controlled local tool

=== Purpose

The local tool supports the approved credential-management sequence and reduces repetitive manual administration.

It is not an independent release authority.

It does not:

* Authorize a release.
* Merge a promotion pull request.
* Approve a protected signing job.
* Cancel a workflow.
* Create or rotate an Apple credential.
* Independently decide whether a failed delivery may be retried.

The tool operates against the explicitly identified repository and GitHub environment.

The implementation should reuse the existing GitHub CLI and repository verification scripts wherever practical.

The final script name and location remain implementation details.

=== Execution authority

Credential-provisioning operations are performed locally by an authorized operator on a trusted computer.

The operator must have the permissions required to manage secrets in the designated GitHub environment.

The tool must not be executed as a GitHub Actions workflow.

The existing repository rule concerning AI-assisted development remains applicable:

An AI assistant must not read, handle, print, provision or remove actual credential values.

Credential-free inspection and verification commands may be executed by a person or assistant with sufficient permissions to inspect the relevant metadata.

Permission to inspect repository source does not necessarily imply permission to inspect secret metadata, environment settings or organization-level configuration.

Insufficient permissions must be reported explicitly.

=== Commands

[cols="2,5,2",options="header"]
|===
| Command | Behavior | Credential handling

| `status`
| Reports relevant repository and environment configuration, protection rules, designated credential names and their presence or absence.

Reports credential age where reliable metadata is available.

Distinguishes observed configuration from declared requirements and inaccessible information.
| None.

| `check-promotion`
| Performs the applicable read-only readiness checks against the specifically identified promotion pull request.

Reports `READY` only when all mandatory prerequisites have been established.

Otherwise reports the remaining blockers.
| None.

| `provision`
| Revalidates the relevant promotion readiness conditions.

Uploads the three designated credentials from operator-selected local sources into the authorized environment.

Verifies successful provisioning.

If provisioning fails partially, initiates removal of the credentials already provisioned.
| Operator-controlled access to credential values.

| `verify`
| Verifies the expected presence or absence of the three designated Apple credentials without retrieving their values.

Supports verification after provisioning and after cleanup.
| None.

| `cleanup`
| Removes the three designated Apple credentials from the selected environment and performs the applicable absence verification.

Remains available regardless of delivery outcome or authorization state.
| Deletes designated secrets only.
|===

The command names establish the intended operational interface.

Their exact argument syntax and implementation remain subject to WP-A1.

== Promotion readiness verification

The `check-promotion` command establishes whether the specifically identified promotion pull request is ready for credential provisioning.

It should reuse existing authorization and verification mechanisms rather than independently reimplement their rules.

Applicable checks include:

* Correct repository and target environment.
* Correct source and target branches.
* Promotion pull request approval and merge readiness.
* Required CI and security checks.
* Valid written release authorization.
* Applicable authorization-bound implementation identities.
* Authorized application source.
* Selected build or staging delivery.
* Verified inherited version information.
* Applicable build-number encoding and consumption restrictions.
* Correct signing environment protection.
* Absence of the three designated Apple credentials.
* Absence of conflicting waiting or running delivery operations.
* Applicable store-side prerequisites.
* Intended tester group or production distribution prerequisites.

The readiness checks must distinguish between:

* Automatically verified prerequisites.
* Prerequisites verified manually by the operator.
* Prerequisites that could not be verified.

The tool must not report an inaccessible prerequisite as satisfied.

A source discrepancy between the Magic APK and the promoted iOS source is reported but does not independently prevent staging delivery (DEC-33).

Production validation requirements remain subject to UNR-06.

=== Binding readiness to the intended promotion

A successful readiness check applies to a specific promotion pull request and its checked source, authorization and target.

A previously successful check must not automatically authorize provisioning for a different or subsequently modified pull request.

Before provisioning, the tool revalidates the applicable readiness conditions.

Before merging, the operator verifies that the approved promotion has not materially changed since those checks.

The implementation must detect relevant changes to:

* Promotion source revision.
* Authorization state.
* Bound implementation files.
* Target branch.
* Required CI status.
* Conflicting workflow activity.

The exact mechanism for preserving the readiness context remains an implementation question.

A transient local session flag alone is not sufficient proof of current readiness.

== Credential provisioning

=== Supported credential sources

Credential values originate from local sources explicitly selected by the operator.

Possible sources include:

* A locally retained credential file.
* Standard input.
* An operating system credential store.

The tool must not establish its own permanent credential store.

It must not unnecessarily copy the original credential.

Long-term storage of the original Apple credential remains outside the scope of the tool.

=== Provisioning restrictions

Provisioning is refused when:

* The repository or target environment is not explicitly identified.
* The target environment is not supported.
* The promotion is not approved and ready.
* The applicable authorization is absent, invalid or withdrawn.
* A relevant readiness check fails or cannot be established.
* The promotion has already been merged.
* A conflicting delivery workflow is waiting or running.
* Any of the three designated Apple credentials is already present unexpectedly.
* The requested credential operation exceeds the tool's permitted scope.

Production provisioning requires explicit selection and confirmation of the production environment.

The tool must not silently default to production.

No force option may bypass the required readiness or environment checks.

=== Partial provisioning failure

Provisioning consists of multiple external operations.

One credential may be uploaded successfully before another upload fails.

Consequently, provisioning must not be treated as an indivisible operation.

If any upload fails:

. Stop further provisioning.
. Report that provisioning did not complete.
. Remove any designated credentials already provisioned by the operation.
. Verify their absence.
. Report any remaining credential or unverifiable cleanup result as an operational incident.

The operator must not merge the promotion until complete provisioning and presence verification have succeeded.

== Credential verification

The verification operation checks credential metadata, not credential values.

=== Presence verification

Successful presence verification establishes that:

* All three designated credential names exist in the intended signing environment.
* They do not exist in prohibited scopes.
* They do not unexpectedly exist in the other signing environment.
* The observed state satisfies the applicable infrastructure requirements.

Credential presence does not establish that the values are correct, current or accepted by Apple.

The delivery workflow establishes whether the credentials can perform the authorized operations.

=== Absence verification

Successful absence verification establishes that the three designated Apple credential names are absent from:

* The staging signing environment.
* The production signing environment.
* Applicable repository-level secret scopes.
* Applicable organization-level secret scopes.

The operation must distinguish verified absence from lack of inspection permission.

If a relevant scope cannot be inspected, the result is incomplete.

An appropriately authorized person must establish the remaining prerequisite.

The tool must not interpret an empty or failed API response as verified absence.

Unrelated secret names and values are not affected.

== Credential cleanup

Cleanup is available independently of the current release authorization or workflow state.

It must remain available after:

* Successful delivery.
* Failed delivery.
* Partial provisioning.
* Cancellation.
* Abandoned promotion.
* Expired authorization.
* Local operator interruption.

Cleanup removes only the three designated credentials from the explicitly selected environment.

It does not delete unrelated secrets.

Unexpected credentials found in another environment or prohibited scope are reported and require appropriately authorized remediation.

Cleanup must be safe to execute repeatedly.

Already absent credentials are not an error.

The cleanup operation must report whether absence has actually been verified.

A successful delete request alone does not establish verified absence.

== Safety requirements

. Credential values must never appear in terminal output, command-line arguments, shell history, logs, audit records or retained workflow evidence.

. Credential values are transferred to the credential-upload mechanism through a protected input channel, preferably standard input to `gh secret set`.

. The tool does not introduce permanent local copies of credential values.

. Temporary files, if technically necessary, require appropriate access restrictions and reliable cleanup. Prefer implementations that avoid creating them.

. The permitted Apple credential names are explicitly restricted to the three designated names.

. The permitted provisioning environments are explicitly restricted to the staging and production signing environments.

. Credential provisioning at repository, organization or Dependabot scope is prohibited.

. A failed readiness check, incorrect repository, incorrect environment or insufficient permission causes refusal.

. No option may bypass the established provisioning sequence.

. Cleanup remains available independently of provisioning restrictions and authorization state.

. The tool must not execute untrusted repository or dependency code while handling credential values.

. GitHub CLI authentication and permissions must be appropriate for the requested operation.

. Diagnostic and error handling must not expose credential values.

=== Dry-run behavior

Mutating commands should support a credential-free dry-run mode.

Dry-run mode reports the intended operations and performs applicable read-only checks.

It must not:

* Read actual Apple credential values.
* Upload credentials.
* Remove credentials.
* Modify repository configuration.
* Claim that provisioning or cleanup has occurred.

=== Operational audit information

The tool records sufficient non-secret information to establish:

* Operation timestamp.
* Operator identity where available.
* Repository and target environment.
* Requested operation.
* Designated credential names.
* Operation result.
* Relevant promotion or workflow identity.

No credential value is included.

The audit information may be retained locally or incorporated into the applicable delivery evidence.

The implementation should avoid introducing an additional independently maintained operational record where existing evidence mechanisms suffice.

=== Exit status and messages

The tool provides distinguishable results for:

* Successful operation.
* Failed readiness verification.
* Unexpected credential state.
* Insufficient permissions.
* Incorrect repository or environment.
* Incomplete provisioning.
* Incomplete cleanup.
* Invalid command usage.

Messages must explain in ordinary operational language:

* What happened.
* Whether the requested operation completed.
* Whether credentials may remain present.
* What the operator must do next.

== Interruption, abandonment and cancellation

=== Principles

Every operation involving temporary credentials must conclude with their removal and verified absence.

A waiting or executing workflow must not be left unattended indefinitely while credentials remain provisioned.

The operator supervises the delivery and initiates cancellation where necessary.

The tool itself does not merge pull requests, approve jobs or cancel workflow executions.

The existing prohibition against re-running a failed authorized staging delivery with a consumed number remains applicable.

An indeterminate upload outcome must not be interpreted as permission to reuse the number.

=== Operational situations

[cols="3,5,3",options="header"]
|===
| Situation | Required action | Result to establish

| Readiness fails before provisioning.
| Do not provision credentials or merge the promotion.
| No credential exposure occurred.

| Provisioning fails partially.
| Stop provisioning, remove any credentials already provisioned and verify absence.
| No designated credentials remain unexpectedly present.

| Promotion is abandoned after provisioning but before merge.
| Run cleanup and verify absence.
| Credentials removed. No delivery initiated.

| Promotion has merged but signing approval is abandoned.
| Cancel the workflow, establish its termination where possible, remove credentials and verify absence.

Withdraw the authorization through the applicable reviewed procedure.
| No further authorized execution. Credential absence verified.

| Signing approval remains pending beyond the permitted waiting period.
| Cancel the waiting delivery and perform cleanup.

Record the abandoned operation.
| Credentials do not remain provisioned indefinitely.

| Signing job is cancelled before the upload.
| Request cancellation and inspect the resulting workflow state.

Remove credentials and verify absence.

Establish whether any upload operation could already have occurred.
| Workflow outcome recorded. Number consumption preserved.

| Cancellation or failure occurs during or after Apple upload.
| Establish the workflow outcome and inspect App Store Connect for the applicable application version and build number.

Remove credentials and verify absence.

Record the outcome as indeterminate if it cannot be established reliably.
| No unsafe reuse of a potentially delivered number.

| Delivery completes successfully.
| Verify the delivery result, remove credentials and verify absence.

Complete the authorization closeout.
| Successful delivery evidence and verified credential removal.

| Delivery fails.
| Inspect and record the failure.

Remove credentials and verify absence.

Apply the applicable recovery procedure.
| Failure recorded and credentials removed.

| Local tool or operator computer becomes unavailable.
| An appropriately authorized administrator performs manual credential removal through GitHub.

Verify absence independently where possible.

Record the manual intervention.
| Credential cleanup does not depend on one workstation or one tool.

| GitHub or network failure prevents cleanup.
| Report cleanup as incomplete.

Attempt removal through an available authorized access path.

Escalate to another authorized operator where necessary.

Do not initiate another delivery while the outstanding credential state remains unresolved.
| Verified removal before subsequent delivery.

| Credential exposure is suspected.
| Stop the affected operation, initiate credential cleanup and notify the CTO.

Apply the applicable incident response and revocation procedure.
| Exposure assessed and appropriate containment established.
|===

Removal of GitHub secrets does not revoke the original Apple API key.

Emergency revocation and replacement remain subject to the applicable credential-custody and incident-response policy.

=== Credential exposure duration

The operational procedure requires a finite permitted waiting period for provisioned credentials.

The exact duration has not yet been established.

WP-A1 must propose an appropriate value based on:

* Expected promotion preparation time.
* Expected signing approval delay.
* Workflow execution duration.
* Operator supervision requirements.
* Available cancellation and cleanup mechanisms.

A concrete duration must be established before unattended or prolonged operational waiting is permitted.

Until then, the existing supervised manual procedure remains applicable.

No assumption is made that GitHub automatically expires the provisioned secrets.

=== Workflow cancellation limitations

The existing workflows reportedly contain temporary credential-file cleanup steps.

Their presence does not establish that cleanup succeeds under every cancellation scenario.

The implementation must investigate and demonstrate:

* Cancellation before signing approval.
* Cancellation during signing.
* Cancellation during credential-file use.
* Cancellation during Apple upload.
* Workflow timeout.
* Forced termination.
* Runner disposal and temporary-file cleanup.

An `always()` condition alone is not sufficient evidence of reliable cleanup under every termination mode.

The corresponding investigation is `FQ-14`.

== Credential-free verification and tests

Development and testing of the operator tool must not require actual Apple delivery credentials.

Use controlled fixtures, simulated GitHub responses and synthetic credential values.

A stub GitHub CLI may be used to inspect the tool's external operations.

The tests must establish the following properties.

[cols="2,4",options="header"]
|===
| Area | Required verification

| Credential confidentiality
| Synthetic credential values do not appear in command arguments, output, logs, retained files or diagnostic information.

| Repository and environment selection
| Incorrect repositories, unsupported environments and unintended production selection are rejected.

| Promotion readiness
| Provisioning is refused for invalid, modified, already merged or unapproved promotions.

| Existing credential state
| Unexpected presence of any designated credential prevents provisioning.

Unrelated authorized secrets are not modified.

| Partial provisioning
| Failure after provisioning one or two credentials initiates appropriate cleanup.

| Presence verification
| Missing designated credentials, incorrect environment and prohibited placement are detected.

| Absence verification
| Remaining designated credentials and inaccessible inspection scopes are reported correctly.

| Cleanup
| Cleanup works after successful delivery, failure, cancellation, partial provisioning and abandoned operations.

Repeated cleanup is safe.

| Dry run
| No credential value is read and no external state is modified.

| Permission failures
| Permission failures are reported without being interpreted as verified absence.

| Readiness changes
| Changes to the promotion source, authorization or relevant infrastructure invalidate stale readiness results.

| Interruption handling
| Local interruption and externally failed operations produce explicit incomplete-state results where cleanup cannot be verified.
|===

Credential-free tests establish the behavior of the local tool.

They do not independently establish the behavior of GitHub-hosted workflow cancellation or Apple's delivery infrastructure.

Those properties require the applicable platform-level investigation and controlled rehearsal.

== Implementation boundaries

WP-A1 implements the local operator tool and supporting operational procedure.

WP-A2 provides the applicable read-only infrastructure and readiness verification.

Existing verification scripts and GitHub CLI mechanisms should be reused rather than duplicated.

The work package does not itself authorize changes to:

* The Apple credential's privilege level.
* Long-term credential ownership or custody.
* Credential rotation or revocation policy.
* Production Android signing credentials.
* Existing authorization-bound workflow files outside the applicable reviewed change procedure.
* Production release acceptance requirements.

Any workflow modification required for reliable interruption handling follows the bound-file change procedure in xref:ch09-migration-sequence.adoc#ch09[Chapter 9].

Long-term Apple credential arrangements remain governed by UNR-02.

== Implementation acceptance

The local operator tool is accepted when it demonstrates that:

* The approved eight-step procedure remains unchanged.
* Credential operations are explicitly operator-controlled.
* Provisioning is restricted to an approved and ready promotion.
* Credential values are not exposed through the tool.
* Only the designated credentials are managed.
* Incorrect environments and prohibited scopes are rejected.
* Partial provisioning failures are handled safely.
* Cleanup remains available independently of delivery outcome.
* Credential absence is verified rather than assumed.
* Incomplete verification is clearly reported.
* Existing repository and release authorization guarantees remain intact.
* The tool reduces operational administration rather than introducing another release-management system.

The tool assists the operator.

It does not replace the operator's responsibility for supervising the credential exposure period and confirming the conclusion of the authorized delivery.
