[[ch05]]
= Requirement-to-enforcement matrix
:description: Stable release-framework requirements, their architectural basis, existing enforcement mechanisms and outstanding implementation work.

*Scope:* Governance, versioning, authorization, credentials, application builds, delivery, evidence, documentation and infrastructure requirements.

*Status:* Proposal for review. The matrix distinguishes established requirements, existing implementation, incomplete enforcement and proposed mechanisms.

== Reading the matrix

Each requirement has a stable identifier.

The requirement column describes the approved target behavior, except where a requirement is explicitly identified as proposed or dependent on an unresolved decision.

The mechanism column describes the currently known implementation, not the intended future implementation.

Implementation observations originate from the release infrastructure audit and the demonstrated staging delivery. They must be reconfirmed where subsequent implementation depends on them.

The classification follows xref:ch01-scope-and-method.adoc#ch01[Chapter 1].

Enforcement types:

[cols="1,4",options="header"]
|===
| Type | Meaning

| AUTO
| The requirement is enforced automatically within its stated implementation scope.

| PARTIAL
| Enforcement is incomplete, or combines automated mechanisms with human-controlled operations.

| HUMAN
| Enforcement depends principally on human compliance.

| NONE
| No mechanism enforcing the target requirement has been established.
|===

Automatic enforcement does not imply comprehensive verification.

A requirement may have an existing mechanism while its approved extension remains unimplemented.

The gap column identifies outstanding implementation work, verification, exception handling or unresolved decisions.

A proposed mechanism does not become an approved architectural requirement merely through inclusion in this matrix.

Until the target architecture takes effect, the existing implementation remains governed by the transitional arrangements in xref:ch09-migration-sequence.adoc#ch09[Chapter 9].

Superseded requirements are retained only in the historical record of xref:ch04-exceptions-and-reconciliation.adoc#ch04[Chapter 4].

Production-specific requirements use the prefix `PRD` and are defined in xref:ch10-production-extensions.adoc#ch10[Chapter 10].

== Enforcement principles

The following principles apply when implementing the outstanding mechanisms.

=== Preserve existing guarantees

Existing authorization, environment separation, signing isolation, artifact verification and repository protection must not be weakened merely to accommodate the target build architecture.

Changes to authorization-bound files follow the reviewed implementation procedure.

Existing security assertions remain applicable unless explicitly replaced by equivalent or stronger assertions.

=== Prefer existing mechanisms

Existing workflows, verification scripts, manifests and tests should be consolidated and reused wherever practicable.

A new component is justified by an identified requirement or implementation gap, not by architectural preference alone.

=== Distinguish a requirement from its implementation

An architectural requirement defines the property that must hold.

The mechanism defines how that property is achieved.

Where the mechanism remains unresolved, the requirement must not prescribe an unverified implementation as if it were already approved.

This distinction applies particularly to:

* Version allocation storage.
* Historical build-number initialization.
* Persistent artifact and evidence storage.
* Generated Git references.
* Workflow write permissions.
* Repository and reference protection.
* Signing-key custody.
* Machine-readable infrastructure declarations.

=== Verify the actual behavior

Implementation acceptance requires appropriate evidence.

Depending on the requirement, this may include:

* Automated tests.
* Workflow execution evidence.
* Repository configuration verification.
* Artifact inspection.
* Failure and cancellation testing.
* Concurrency testing.
* Manual operational verification.

The existence of a script, configuration file or documented procedure is not sufficient evidence that its required behavior has been demonstrated.

=== Preserve authorization boundaries

An operational mechanism must not silently resolve an outstanding CTO decision.

Where implementation encounters a genuine security, operational or distribution policy question, the corresponding unresolved decision must be addressed before the affected mechanism becomes operational.

Unrelated implementation work may proceed independently.

== Requirement maintenance

Requirement identifiers remain stable.

When a requirement changes:

. Identify the architectural decision or technical finding that justifies the change.
. Update its authoritative normative definition.
. Reconcile this matrix and the corresponding enforcement mechanism.
. Update affected verification and acceptance tests.
. Preserve the rationale of superseded requirements where historically relevant.

A retired identifier must not be reassigned to an unrelated requirement.

Requirements must not be duplicated into independently maintained normative documents.

Where a machine-readable requirement register or generated matrix is introduced, its relationship to the authoritative human-readable documentation must be explicit.

There must not be two independently maintained authorities for the same requirement.
