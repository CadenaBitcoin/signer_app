[[sta-as-built]]
= As-built overview (STA-01)
:description: What the repository implements today for building, authorizing, signing and delivering the Cadena Signer, set against the approved target architecture.
ifndef::specdir[:specdir: ../release-process/]
ifndef::docsdir[:docsdir: ../]

*Scope:* The current state of the release framework: mechanisms, authorization state, exceptions, documentation dependencies and outstanding work. It states implementation status. It defines no requirement.

*Status:* Current as of `development` `b4eabbf` plus step P1 (2026-11-28). Maintained with every change that alters a mechanism listed here. Normative requirements are in the specification (xref:{specdir}index.adoc#ch01[Chapter 1] and following). This page changes no decision.

== How to read this page

The specification states what the framework must be. This page states what exists. The two differ on purpose until the migration of xref:{specdir}ch09-migration-sequence.adoc#ch09[Chapter 9] is complete. The state words and evidence labels are those of the xref:{docsdir}00-front/conventions.adoc#conv-conventions[conventions page].

*No target mechanism is active on any branch.* Magic, persistent allocation, the iOS-only staging promotion, version inheritance, persistent build records and the operator credential tool do not exist in the repository. A branch-by-branch activation table (Chapter 9, step P6) is not yet needed. It is added when the first of these reaches `development`.

Where a row cites a decision (`DEC-NN`), the requirement is in Chapter 2. Where it cites an exception (`EXC-NN`), the disposition is in Chapter 4.

== Mechanisms

[cols="3,2,5,3",options="header"]
|===
| Mechanism | State | What exists and the evidence | Approved target

| Branch model and protection
| Current
| `development` (default), `staging`, `production`. Promotion by reviewed pull request, merge method only, forward only (`GOVERNANCE.md`). The rulesets were VERIFIED by the release audit and are not re-verified by P1. Required status checks and mandatory signed-commit enforcement are reported as not active (`RELEASE_POLICY.md` 2.3, checked 2026-11-17; DOCUMENTED BUT NOT VERIFIED today).
| Required checks and commit-signature enforcement: `BRN-03`, WP-A3.

| Application version and build number
| Current
| One declaration, `version:` in `pubspec.yaml` (`1.0.5+10005002` at this commit). Both platforms carry the same values. A person advances the build number in a reviewed commit. `tool/verify_version.sh` checks the wiring and `tool/test_release_versioning.sh` the policy. VERIFIED by those tools in the P1 baseline run.
| One allocated sequence and inherited version information: `DEC-30` to `DEC-32`, `DEC-37`, `DEC-38`. Not implemented. See <<sta-versioning>>.

| Published-version floors
| Current
| `config/release/published_versions.json` records Android `1.0.3` (`1000034`) and `1.0.4` (`1000035`). It records no iOS floor. `tool/build_manifest.py` enforces that a new Android build number is above the recorded ones.
| Safe historical initialization: `DEC-37`, `VER-13`, `VER-14`.

| Consumption of build numbers
| Current, human-controlled
| A failed or interrupted delivery is recovered through a new build number, a new written decision and a new reviewed promotion (`DEC-13`). Nothing enforces it automatically (`VER-04`). Demonstrated by the recovery from `10005001` to `10005002`.
| Allocation before compilation by Magic: `DEC-32`. Not implemented.

| Release identifiers `vX.Y.Z-rc.N`
| Current, superseded
| The validation tools and their tests still accept and check `-rc.N` identifiers (`tool/verify_version.sh`, `tool/build_manifest.py`, `tool/test_release_versioning.sh`). `RELEASE_POLICY.md` 3.1 and 7.3 still describe them.
| Ended by `DEC-29`. Removal belongs to the cutover (P6).

| Build triggers
| Current
| A push to `staging` runs `build-variants` (`android-staging-apk`, `ios-staging`), `android-ci-validation`, `ios-ci-validation`, and `ios-staging-delivery` (which refuses unless its authorization record says `AUTHORIZED`). A push to `production` runs the three production variants of `build-variants`. `build-variants` and `android-ci-validation` can be started by hand. (`docs/RELEASE_TRIGGERS.md`; workflow `on:` blocks.)
| Magic by hand; the staging promotion delivers iOS only; the production promotion builds three artifacts: `DEC-33` to `DEC-36`, `DEC-39`. Not implemented.

| Android staging APK
| Current
| A debug-signed CI validation build, "not approved for public distribution" (`docs/ANDROID_CI.md`). It uses the staging flavor and `config/build/staging.json`. No persistent signing identity or access policy exists (`EXC-03`).
| Magic as the sole routine staging APK mechanism, persistent storage, signing identity via `UNR-01 (a)`: `DEC-32`, `DEC-35`, `DEC-39`.

| Retained artifacts
| Current, inactive
| The mechanism encrypts verified artifacts to public keys (`docs/RETAINED_ARTIFACTS.md`). `config/release/artifact_recipients.txt` contains no key, so routine retention is off. VERIFIED by reading the file.
| Persistent APK availability and build records: `DEL-07`, `EVD-05`, WP-C3.

| Android production release
| Current, manual
| Signing is explicit (`CADENA_SIGNING=release`) and local, by the upload-key holder (`docs/ANDROID_RELEASE.md`). Version `1.0.4+1000035` was published. No workflow signs or uploads an Android release.
| Production APK, AAB and IPA from one source: `DEC-34`, WP production work at P9.

| iOS staging delivery
| Current, demonstrated once
| Workflow `ios-staging-delivery.yml` has three jobs. `authorize` and `build` run without a secret. `sign` runs in the protected environment `ios-hosted-signing-stg`, whose required reviewers must approve, verifies the IPA (V1 to V9) and uploads it to the staging App Store Connect application. It delivered `1.0.5+10005002` (run `46005605593`, `staging` `f31e598`). Evidence: `docs/release-records/staging-delivery-1.0.5-10005002.adoc`. Installation and a basic smoke test are CTO-REPORTED. Wallet and DLC functionality were not validated (`EXC-12`).
| Staging promotion inherits version information from a Magic build and reports source differences: `DEC-33`, `EVD-06`, `EXC-13`. Not implemented.

| Release authorization (staging)
| Current
| The record `docs/release-records/ios-staging-authorization.md` binds the version, the application identity, the certificate, the native library and the exact blobs of the workflow, the gate and seven tools. `tool/check_staging_authorization.sh` refuses unless the record says `AUTHORIZED`, and it reads the record on the current tip of `development`. 48 gate scenarios pass in the baseline run. The status at this commit is `WITHDRAWN`.
| Structured data separate from prose (P2): `DOC-03`, WP-A5.

| Release authorization (production, iOS)
| Current, withdrawn
| The workflow `ios-hosted-signing.yml` runs only by hand. Its gate reads `docs/release-records/ios-1.0.4-1000035.md`, status `WITHDRAWN`. Upload exists behind the gate (PR #134); the workflow's name still says "no upload" (`REC-05`). The production pipeline is not operationally complete.
| Production workflows and gate (W4, P9): `PRD-NN`.

| Temporary Apple credentials
| Current, manual
| Three secrets, provisioned for one authorized delivery and removed afterwards. The `10005002` delivery provisioned and verified them before the promotion merge, which is the order `DEC-28` makes the only supported one. They were removed afterwards (the record). The Admin key itself was not revoked. External custody is not verified (`DEC-09`, `UNR-02`).
| The local operator tool, interruption handling and absence checks: `CRD-05`, WP-A1. Not implemented. Until then the manual procedure of `IOS_STAGING_DELIVERY.md` section 8.1 and Chapter 8 applies.

| Native `dlc_wallet` framework
| Current
| Pinned by hash in the record (`EXC-07`). Prebuilt binaries are committed. Their provenance and release process are not documented (`UNR-07`).
| `UNR-07`.

| Build and delivery evidence
| Current, partial
| `cadena-build-manifest/1` for each build. Delivery records are written by hand and version-controlled. There is no persistent record of allocations, failures or unpublished builds, and no source-comparison record.
| `EVD-05` to `EVD-07`, WP-C3.

| Read-only infrastructure verification, repository hardening
| Not implemented
| Settings and prerequisites are checked by a person (`DEC-22`). Secret scanning, push protection and the CodeQL exception `EXC-05` are open.
| WP-A2, WP-A3.
|===

[[sta-versioning]]
== Current and proposed versioning behavior

Today the version is the one declaration in `pubspec.yaml`, advanced by a reviewed commit, with human-controlled consumption. Everything about allocation, the numerical encoding (`XX.YY.ZZ.RRR`), one shared sequence and inheritance is an approved target whose storage mechanism is under investigation (`FQ-01`, `FQ-02`, `FQ-03`, `FQ-12`).

`docs/RELEASE_VERSIONING.md` documents the current behavior in its committed form. Its working copy in the owner's checkout is an unmerged rewrite, dated 2026-11-24, with staged and unstaged changes. It is preserved untouched and is not reflected here.
